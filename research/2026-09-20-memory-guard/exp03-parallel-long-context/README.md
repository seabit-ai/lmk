# exp03 — 长上下文下，并行 2 还"各自几乎不慢"吗？

日期 2026-09-20。起因：验看状态看板时看到，一个 27k 上下文的请求与一个短请求并行 decode，各只有 18–20 tok/s；
而 exp01 M2 的"各 34 tok/s、合计 1.7×"是两个**几十 token** 的短 prompt 量出来的。agent 的常态是长上下文，
`requests.max_parallel: 2` 的缺省依据需要在长上下文下重量。

## 方法
`run.py <label> <n>`：n 个线程同时发同一份 27,190 token 的会话（lmk 已缓存 27,136，所以几乎没有 prefill），`max_tokens=200`，
记各自的 decode 速率。L1：1 个；L2：2 个同时。载荷含私人内容，在 nova `2026/2026.0920.M3uOmlxVsLmk/payload-long.json`。

## 预期（跑之前写的）
- L1：约 33 tok/s（此前同一载荷量得 349 token / 10.5s）。
- L2：每个约 18–22 tok/s，合计约 40，即 **1.2× 左右**——远不如 exp01 的 1.7×。依据就是看板上那次偶然观察。把握 70%。

## 结果
原始输出 `raw/results.jsonl`。

| | 每个请求 | 合计 | 相对 1 个 |
|---|---|---|---|
| L1：1 个（27k 上下文） | 33.0 tok/s | 33.0 | 1.0× |
| L2：2 个同时 | 16.0 / 16.8 | 32.8 | **1.0×** |
| L1 复测 | 33.6 | 33.6 | — |

### 对照预期
- L1 ✅。L2：预期合计 1.2×，实测 **1.0×**——比预期更差，方向一致。
- **exp01 的结论要加限定词**：并行 decode 的收益只在短上下文下存在（两个几十 token 的请求：1.7×）。27k 上下文下，
  每步 decode 要对 27k 个 token 的 KV 做注意力，单个请求已经把 GPU 吃满；两个一起只是各分一半。
- 对用户的含义：长上下文（agent 的常态）下，并行不产生吞吐，只改变等待的形状——两个请求同时以半速出字，
  而不是一个全速、另一个排队。总完成时间相同；先到的那个反而更晚写完。
