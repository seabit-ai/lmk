# 预热（warmup）能否"不打扰"：调查笔记（2026-09-24）

背景：kitten 的设计 `docs/design/2026-09-24-llm-progress.md` §8 与本次 SAD——后台预热由 lmk 保证不打扰：
只在空闲时开始，每算完一块检查一次，有真实请求在等就停下让路；kittend 每 5 分钟把最近活跃会话的前缀交给
`POST /lmk/v1/warmup`，已经热的几十毫秒返回。

## 发现

- **PW-001 取消的 prefill 保住已算完的块。** prefill 中途被取消后，同一前缀的下一个请求命中了取消前实际算完的全部块
  （14,583 中命中 12,288 = 6 × 2048）。让路不会白算——"每块检查一次、有人等就停"的设计成立。（exp01）
- **PW-002 客户端断开的检测滞后约两块。** 断开后的第一次流写入进了 socket 缓冲区不报错，第二次才失败；
  在约 325 token/s 下约 13 秒。对预热无影响（让路走 lmk 内部标记，不靠写 socket）；对普通请求意味着用户取消后
  GPU 还会多忙十几秒。（exp01）
- **PW-003（推理，未实测）chat template 改写更早消息的风险被 warmup 的 "." 收尾中和。** Qwen 系模板在后面还有 user 消息时
  会去掉更早助手回复里的思考内容。warmup 在历史末尾补一条 `"."` user 消息收尾，真实请求在同一位置是新的 user 消息——
  两者渲染时最后一轮助手回复后面都有 user 消息，改写一致，分叉点仍在补的那条消息处。需要时用一个实验确认。

## 决策记录

- 让路机制采用"lmk 每块检查内部标记"（PW-001 使之可行）。
- 否决："预热请求本身只发一小段前缀、kittend 分段推进"——它是 PW-001 为否时的后备方案；现在不需要，且要 kittend 按消息切段、
  粒度不可控。
