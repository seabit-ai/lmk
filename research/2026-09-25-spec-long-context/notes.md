# 投机解码在长上下文下还赚不赚（27B 推荐组合，本机）

日期 2026-09-25。起因：用户说"投机解码到大上下文会变得很慢"；我们开草稿的数只量到约 22k（owner 今天的 agent 流量）。
编号 SLC-xxx。条件（下文都是）：m3u（M3 Ultra 60 核，96 GB），`qwen3.8-27b-4bit`、`kv_cache_bits: 8`、草稿器 dflash2（4 位）、思考关，
单请求，前缀已在 cache（只量 decode），前缀是公开源码（mlx-engine / mlx_lm / mlx_vlm），每格 256 token × 3 次，lmk main 5952212、引擎 42a248c。

## 目的
1. 开/关草稿的 decode 速度比随上下文（8k / 32k / 64k / 128k）怎么变，分散文与代码。
2. 有没有一档开草稿比关慢；原因是接受率还是校验代价。
3. （exp02）同条件换 16 位 KV：kv8 的代价是否随上下文涨、内存差多少。（exp03）采样的一轮比贪心贵的 ms 在哪。

## 发现
- **SLC-001 到 128k 开草稿都不比关慢**（exp01）：贪心 code 1.50 / 1.51 / 1.43 / 1.28×，prose 1.12 / 1.27 / 1.24 / 1.23×；
  128k 上 code 19.7 对 15.4 tok/s、prose 18.8 对 15.2。"大上下文变很慢"在本机这个组合上没复现（其他机器、其他实现、更宽的校验、
  冷 prefill 都没量）。把握：高（每格 3 次，离散 ≤ 8%）。
- **SLC-002 加速缩小来自一轮相对单步变贵，不是接受率掉**（exp01，推算）：code 的一轮 ÷ 关草稿的一步 = 2.50 / 2.60 / 2.66 / 2.76，
  每轮吐出 3.5–3.9 个 token 基本不变；接受率各档 code 71–83%、prose 56–63%，不随上下文单调变化（草稿器只看 prefill 尾巴，SPD-018/exp09）。
  prose 的比值平在 1.8 左右，所以 prose 的加速不缩。把握：中（轮数由 255 − 接受数推得，日志没有轮数）。
- **SLC-003 校验宽度自己停在悬崖前**（exp01，推算）：每轮起草 code 约 3.5、prose 约 2.0，即校验宽 4.5 / 3，都在 SPD-015/019 的
  T ≥ 6（`q_len × GQA > 32`，32k 上 70 → 143 ms）悬崖之下。只有把草稿块加宽（后缀草稿、块 8）才会撞上它——那时长上下文的账要重算。把握：中。
- **SLC-004 关草稿本身在长上下文掉得比外推快**（exp01）：35 / 28 / 22 / 15 tok/s（kv8，每步 28 / 36 / 46 / 65 ms）。exp13 的
  bf16 单次前向外推 128k 一步约 48 ms，这里 65。与 owner 流量（关草稿 40–80k 中位 22.5、80k+ 18.9，采样）同一量级。
  把握：高（量到的数）；原因（kv8 反量化 / 服务路径）未分。
- **SLC-005 采样的散文几乎不赚**（exp01，32k）：模型缺省采样下 prose 1.02×（贪心同格 1.27×），code 1.40×（贪心 1.51×）。
  采样一轮比贪心同宽度贵约 10 ms（prose 74 对 64 ms，每轮起草都是 2.0），接受率 54% 对 63%。agent 真实流量是采样；owner 日志
  13–22k 的 ≈1.2× 里含工具调用体（复述型，接受高，SPD-035），纯散文段可能接近打平。把握：中（只有 32k 一档、3 次）。
- **SLC-006 kv8 下贪心开/关文本 8 格全分叉**（exp01）：每边 3 次内部一致、两边不同，code 也分叉。与 SPD-018 已知的量化注意力
  L>1 / L=1 不位级一致同源（未单独验证）。速度比较因此是"同一题两段文本"。把握：高（现象）/ 中（归因）。

- **SLC-007 16 位 KV 在长上下文 decode 明显更快，从 32k 起**（exp02）：关草稿每步 kv16 27.0 / 31.0 / 35.9 / 45.2 ms，kv8 28.3 / 36.2 / 46.3 / 65.1
  （8k / 32k / 64k / 128k）；即 128k 22.1 对 15.4 tok/s（快 44%），32k 快 16%，8k 快 5%。kv16 斜率 +0.15 ms / 1k 与 exp13 的 bf16 微基准一致，
  kv8 是它的两倍——owner 的假设成立：SLC-004 里 128k 多出来的约 20 ms 是 kv8 路径的代价（量化注意力不走融合 kernel；未进 kernel 层面验证）。
  带宽账（kv16 读的字节多该更慢）在本机不成立。把握：高（每格 3 次，离散 ≤ 1%）。
- **SLC-008 开草稿时 kv16 的好处更大，但加速比（对各自关草稿）不一定更大**（exp02）：128k code 开草稿 31.2 tok/s，kv8 19.7（1.58 倍）；
  一轮 128 对 179 ms（kv8 一轮多出 51 ms，单步只多 20 ms——校验块几行查询在量化路径上按行付费）。对各自关草稿的加速：code 1.45 / 1.54 / 1.49 / 1.41×，
  prose 1.19 / 1.17 / 1.16 / 1.08×（kv8 prose 1.12–1.27×），因为底数也快了。用户感受得到的数是绝对速度：kv16 + 草稿在 128k code 31、prose 24 tok/s，
  kv8 + 草稿 19.7 / 18.8。把握：高（数）/ 中（"按行付费"是由两组 ms 推的）。
- **SLC-009 kv16 的内存账**（exp02 + 引擎公式）：KV 65,536 对 34,816 B/token，128k 8.6 对 4.6 GB。262k 在 kv16 下本机仍装得下（引擎 fitted=262,144），
  按引擎公式余约 17 GiB（kv8 约 25 GiB）；同时在内存里的 token 上限 1.84M → 0.98M（两个长请求并发的余量减半）。进程实测 128k 解码时持有 52–54 GB
  （含 MLX 缓冲池），peak in use 42–43 GB；262k 的请求没跑。把握：高（公式、128k 实测）/ 未测（262k 实跑）。
- **SLC-010 贪心开/关文本分叉不是量化造成的**（exp02）：kv16 下 8 格也全部分叉（每边 3 次内部一致）。SLC-006 的归因（量化注意力 L>1 / L=1）不成立；
  分叉来自批量校验与单步的浮点差本身。现象把握高，具体是哪一层的差没追。
- **SLC-011 kv16 下采样的一轮不比贪心贵**（exp02，32k prose，精确轮数）：采样 60 ms 对贪心 60 ms（kv8 exp01：73 对 64，估的轮数；精确轮数证明估法差 ≤ 1 轮）。
  kv16 下采样 prose 只输在接受率（54% 对 63%）：1.06×。所以 SLC-005 的"采样一轮贵 10 ms"是 kv8 条件下的事实，见 exp03。

- **SLC-012 采样的一轮只比贪心同宽度贵 2–3 ms，不是 10**（exp03，kv8，32k，量的）：校验宽 3 时 prose 一轮 66.7 / 69.3 ms（中位 / 均值）对 64.6 / 66.3，
  code 66.0 / 67.8 对 63.5 / 64.4。SLC-005 的"贵约 10 ms"是 3 次请求的中位数撞上请求间 ±4 ms 的离散（exp01 采样三次 73 / 69 / 76 ms）；
  轮数估法本身没错（SLC-011 的精确轮数）。把握：高（2,262 轮逐轮计时）。
- **SLC-013 多出的 2–3 ms 是采样算子的 GPU 时间，不是同步**（exp03，量的）：第一个位置的采样在校验的关键路径上 +0.9 ms（logsumexp 0.30 + 一次采样 0.85
  对 argmax 0.30），之后每多走一个位置约 0.95 ms（prose 平均多走 1.05 个）→ +1.0；另有"主机变慢的轮"（主机建图慢 2.5–3 倍，一轮 +10 ms）
  采样 30% 对贪心 21%，均值差约 0.9 ms，原因未分离。空同步 < 0.01 ms；单个位置 top_p 的全词表 argsort 0.52、top_k 0.44、categorical 0.34、logsumexp 0.23 ms。
- **SLC-014 向量化一次采完一块只省约 1 ms 一轮（估算）**（exp03）：微基准（真实 32k logits，3 个位置）逐位置 2.68 ms、向量化 1.21 ms、argmax 0.25 ms。
  换上后采样一轮约 67.3–68.3 ms，32k prose 采样 30.8 → 约 31.3–31.7 tok/s，对关草稿 **1.12× → 约 1.14–1.16×**，上限（与贪心同价）1.17×。
  采样与贪心加速的主要差距是**接受率**（prose 53% 对 59%，同宽度多走 8 轮 ≈ 0.5 s / 256 token），要动接受规则（p/q 拒绝采样），不是一轮的代价。
  另一个两边都有的：起草图要等 walk 里 `draft.tolist()` 才提交，GPU 空等主机建图约 3 ms / 轮（上限，未试）。把握：中（估算套量的微基准）。
- **SLC-015 32k 采样 prose 的加速本身离散很大**（exp01 + exp03，kv8）：6 次开草稿采样 27.3–30.9 tok/s（对关草稿 27.4 → 1.00–1.13×，中位约 1.06×），
  贪心 6 次 31.7–35.3。采样下每次请求的接受数不同（124–136），一轮时间也跟着变；3 次的中位数只够报"约 1.0–1.1×"。

## 没量的
- 冷 prefill 时开草稿的代价（DFlash2 在 prefill 时抓隐状态）：两边的前缀都来自 cache，TTFT 相当（128k 3.5–3.9 s）。
- 采样只量了 32k；128k 的采样散文可能跌破 1×——按 SLC-002 的比值不涨推测不会，但没量。
- 思考开、带 tools、两请求并发、别的机器（带宽更低的 Mac 上校验更贵）。
- kv16 下 262k 的真实请求（exp02 只有公式）；kv16 与 kv8 的进程占用并排（exp01 没记内存）；kv16 在 64k+ 的采样行。
- exp03 只在 kv8 / 32k 拆了；"主机变慢的轮"的来源；向量化采样与起草图提早提交都只是估算，没做出来量。

## 把握
SLC-001、004 高；002、003、005 中；006 现象高、归因中（归因已被 SLC-010 否掉）；007、010、011、012 高；008、013 高（数）/ 中（解释）；009 高（公式与 128k）；014 中（估算）；015 高（现象）。都是单机单配置；数在各自的 `exp01-context-sweep/`、`exp02-kv16-context-sweep/`、`exp03-sampled-round-profile/`。

## 决定与后续（2026-09-25）
- **owner 机器改用 16 位 KV cache**（owner："sure, switch"）：依据 SLC-007。已切换并确认 `KV cache 16-bit`；96 GB 仍装得下 262k。
- **待定**：27B 模型页的推荐配置按内存分档（大内存推荐 kv16、小内存留 kv8）——要先量 kv8 一侧的进程内存（本组只量了 kv16）才能定档位线。
- **不做**：逐位采样向量化（SLC-014，估算每轮只省约 1–2 ms，散文采样 1.12→约 1.15×）。采样与贪心的真实差距在接受率（53% 对 59%），
  要追需改接受规则（p/q 拒绝采样），另开题。
- **更正**：SLC-006"开/关草稿分叉由量化造成"不成立（SLC-010：kv16 下同样全部分叉）——是浮点并列。
