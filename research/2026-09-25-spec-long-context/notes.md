# 投机解码在长上下文下还赚不赚（27B 推荐组合，本机）

日期 2026-09-25。起因：用户说"投机解码到大上下文会变得很慢"；我们开草稿的数只量到约 22k（owner 今天的 agent 流量）。
编号 SLC-xxx。条件（下文都是）：m3u（M3 Ultra 60 核，96 GB），`qwen3.8-27b-4bit`、`kv_cache_bits: 8`、草稿器 dflash2（4 位）、思考关，
单请求，前缀已在 cache（只量 decode），前缀是公开源码（mlx-engine / mlx_lm / mlx_vlm），每格 256 token × 3 次，lmk main 5952212、引擎 42a248c。

## 目的
1. 开/关草稿的 decode 速度比随上下文（8k / 32k / 64k / 128k）怎么变，分散文与代码。
2. 有没有一档开草稿比关慢；原因是接受率还是校验代价。

## 发现
- **SLC-001 到 128k 开草稿都不比关慢**（exp01）：贪心 code 1.50 / 1.51 / 1.43 / 1.28×，prose 1.12 / 1.27 / 1.24 / 1.23×；
  128k 上 code 19.7 对 15.4 tok/s、prose 18.8 对 15.2。"大上下文变很慢"在本机这个组合上没复现（其他机器、其他实现、更宽的校验、
  冷 prefill 都没量）。把握：高（每格 3 次，离散 ≤ 8%）。
- **SLC-002 加速缩小来自一轮相对单步变贵，不是接受率掉**（exp01，推算）：code 的一轮 ÷ 关草稿的一步 = 2.50 / 2.60 / 2.66 / 2.76，
  每轮吐出 3.5–3.9 个 token 基本不变；接受率各档 code 71–83%、prose 56–63%，不随上下文单调变化（草稿器只看 prefill 尾巴，SPD-018/exp09）。
  prose 的比值平在 1.8 左右，所以 prose 的加速不缩。把握：中（轮数由 255 − 接受数推得，日志没有轮数）。
- **SLC-003 校验宽度自己停在悬崖前**（exp01，推算）：每轮起草 code 约 3.5、prose 约 2.0，即校验宽 4.5 / 3，都在 SPD-015/019 的
  T ≥ 6（`q_len × GQA > 32`，32k 上 70 → 143 ms）悬崖之下。只有把草稿块加宽（后缀草稿、块 8）才会撞上它——那时长上下文的账要重算。把握：中。
- **SLC-004 关草稿本身在长上下文掉得比外推快**（exp01）：35 / 28 / 22 / 15 tok/s（kv8，每步 28 / 36 / 46 / 65 ms）。exp13 的
  bf16 单次前向外推 128k 一步约 48 ms，这里 65。与 owner 流量（关草稿 40–80k 中位 22.5、80k+ 18.9，采样）同一量级。
  把握：高（量到的数）；原因（kv8 反量化 / 服务路径）未分。
- **SLC-005 采样的散文几乎不赚**（exp01，32k）：模型缺省采样下 prose 1.02×（贪心同格 1.27×），code 1.40×（贪心 1.51×）。
  采样一轮比贪心同宽度贵约 10 ms（prose 74 对 64 ms，每轮起草都是 2.0），接受率 54% 对 63%。agent 真实流量是采样；owner 日志
  13–22k 的 ≈1.2× 里含工具调用体（复述型，接受高，SPD-035），纯散文段可能接近打平。把握：中（只有 32k 一档、3 次）。
- **SLC-006 kv8 下贪心开/关文本 8 格全分叉**（exp01）：每边 3 次内部一致、两边不同，code 也分叉。与 SPD-018 已知的量化注意力
  L>1 / L=1 不位级一致同源（未单独验证）。速度比较因此是"同一题两段文本"。把握：高（现象）/ 中（归因）。

## 没量的
- 冷 prefill 时开草稿的代价（DFlash2 在 prefill 时抓隐状态）：两边的前缀都来自 cache，TTFT 相当（128k 3.5–3.9 s）。
- 采样只量了 32k；128k 的采样散文可能跌破 1×——按 SLC-002 的比值不涨推测不会，但没量。
- 思考开、带 tools、两请求并发、别的机器（带宽更低的 Mac 上校验更贵）。

## 把握
SLC-001、004 高；002、003、005 中；006 现象高、归因中。都是单机单配置；数都在 `exp01-context-sweep/`。
