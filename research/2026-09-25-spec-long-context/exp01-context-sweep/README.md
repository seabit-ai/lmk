# exp01：投机解码（dflash2）开/关 × 上下文 8k / 32k / 64k / 128k 的 decode 速度

日期 2026-09-25。m3u（M3 Ultra 60 核 GPU，96 GB）。lmk main 5952212（分支 `spec-long-context`），`ENGINE_COMMIT` 42a248c。

## 要回答
用户说"投机解码到大上下文会变得很慢"。本机、27B 推荐组合下，草稿开/关的 decode 速度比随上下文怎么变；有没有、在哪一档开草稿反而比关慢；
原因是接受率掉了，还是校验变贵了。

## 条件
- 模型 `qwen3.8-27b-4bit`，`kv_cache_bits: 8`，草稿器 `dflash2`（4 位）——模型页推荐组合里的速度相关部分。
- **思考关**（`thinking: false`）：只看 decode 速度，不让思考段混进"散文 vs 代码"；也是 owner 今天真实 agent 流量的设置。
  推荐组合里的 `reasoning_effort: low` 只在思考开时有意义，这里不设。
- 贪心（`temperature: 0`）：开草稿不改 token 路径（浮点平手除外），开关两边生成的是同一段文本，速度可比。
  32k 上另加模型缺省采样（temp 1.0 / top_p 0.95 / top_k 20，请求里不带 temperature）各 3 次。
- 本机窗口：模型页与 `lmk status` 都是 262,144，128k 在窗口内。

## 方法（`run.sh`，自包含）
- 长前缀：`prefix.py` 按路径排序拼 mlx-engine fork、`mlx_lm`、`mlx_vlm` 的 `.py` 源码（排除 tests，每个文件前一行 `### 路径`），
  用模型的 tokenizer 在 8,192 / 32,768 / 65,536 / 131,072 token 处截断。全是公开代码，嵌套前缀（短的是长的开头）。
- 两种任务（接在前缀后面，同一条 user 消息）：prose = "用散文讲这套代码怎么组织、请求怎么流过，至少 800 词，不许列表/代码"；
  code = "写一个线程安全 LRU cache 模块 + 至少 15 个单测，只输出代码"。`max_tokens: 256`，两种任务都写不完，预期 `finish_reason: length`（记录）。
- 每个条件一个临时 lmk（端口 1236，自己的 `LMK_HOME`，按 PID 杀），先关草稿、后开草稿，**两个不同时在**；两个条件共用一个临时 prompt cache 目录
  （cache 身份不含草稿器，开草稿那一轮直接命中关草稿时算好的前缀，省一半 prefill）。
- 每个（上下文, 任务）：先发一次同样的请求 `max_tokens: 1` 把前缀算进 cache，再发 3 次正式请求。正式请求的 prefill 只剩尾巴，
  decode 速度 = (completion − 1) / (totalMs − ttftMs)，取临时 lmk 的 `LmkChatDone` 行（按 `X-Lmk-Ref-Id` 对上）。报中位数与最小–最大。
  接受率 = Σ`draftAccepted` / Σ`draftDrafted`（每个格子单独算，不混总数）。贪心下记全文 sha，看开/关是否同一段文本。
- **常驻服务（1235）不停**：owner 可能在用。正式请求期间每 0.5 s 读一次常驻的 `/lmk/v1/status`，它有请求在飞、或已答数变了，
  这次作废（`raw/runs.jsonl` 里 `mode: discarded`）、等 20 s 重跑，最多 6 次。（控制者转达过"可以停常驻"的改动，但停服务的操作
  没拿到本机权限，按原方案不停。）
- 注意：DFlash2 草稿器只吃本次请求 prefill 的尾巴（exp09）。cache 命中后尾巴很短——这和 agent 真实用法一样（每轮都命中前缀），
  但意味着草稿器在这里看不到长上下文本身。

## 对比基准（已有的数，条件各不相同）
- SPD-019 / exp13（m3u，27B-4bit，bf16 KV）：一次前向校验 T 个 token，4k：T=1 29 ms、T=5 57 ms；32k：T=1 33.5 ms、T=5 69.8 ms、**T=6 142.5 ms**。
  引擎一轮 DFlash2 约 71 ms（草稿 15 + 校验 55 + 回滚 1）；DFlash2 的校验宽度停在 5（块自适应只看接受率）。
- SPD-020 / exp14（短 prompt，bf16 KV）：code 1.71×（67.6 tok/s）、copyedit 2.05×、story 1.18×。
- owner 今天的 agent 流量（常驻日志，27B-4bit、思考关、kv8、dflash2、模型缺省采样、多为散文 + 工具调用）：13–22k 开草稿 37–39 tok/s，
  关草稿 8–20k 中位 32（≈1.2×，接受 60–65%）；关草稿 40–80k 中位 22.5、80k+ 18.9。开草稿在约 22k 以上没有数。

## 预期（跑之前写）
推导：exp13 里 4k→32k，T=1 每 1k 上下文 +0.15 ms，T=5 +0.46 ms（约 3 倍——5 行查询的注意力各读一遍 KV）。外推到 128k：T=1 ≈ 48 ms，
T=5 ≈ 114 ms，一轮 ≈ 130 ms。每轮出 token（接受数 + 1）：code 约 4、散文约 2.5（常驻看板今天 2.5 / 轮）。
- **P1 关草稿的 decode 随上下文下降**：8k 约 36、32k 约 30、64k 约 25、128k 约 20 tok/s（贪心，prose 与 code 相近）。把握：中。
- **P2 code 的加速随上下文缩小但到 128k 仍 > 1**：8k 约 1.6×、32k 约 1.5×、64k 约 1.4×、128k 约 1.25×。把握：中低。
- **P3 prose 的加速更小，64k 起开草稿不快于关，128k 慢于关**：8k 约 1.15×、32k 约 1.05×、64k 约 1.0×、128k 约 0.9×。把握：中低
  （"在哪一档翻过 1"对接受率很敏感：散文接受 60% 与 45% 差一整档）。
- **P4 接受率基本不随上下文变**（同一任务各档差 ≤ 10 个百分点）：草稿器只看尾巴，上下文长短不进它的输入。code 70–85%，prose 45–65%。把握：中。
- **P5 变慢的原因是校验变贵、不是接受率掉**：由 P4 + 每档开关两边的 ms/token 反推的一轮耗时随上下文涨得比单步 decode 快。把握：中。
- P6 贪心开/关文本：code 多数一致；prose 与 kv8 下可能在几十 token 后分叉（SPD-018、exp01 of spec-with-tools）。分叉不影响速度比较的结论，
  但分叉后两边生成的内容不同，速度比会带一点内容差。把握：中。
- 采样行（32k）：接受率比贪心低 0–10 个百分点，加速比贪心略小。把握：中低。

对预期：
- P1 方向对、幅度落空（猜高了）：关草稿 35 / 28 / 22 / 15 tok/s，押的是 36 / 30 / 25 / 20。128k 的一步 65 ms，我从 exp13 外推的是 48 ms——
  exp13 是 bf16 KV、单次前向的微基准；这里是 kv8、整条服务路径。上下文越长 decode 掉得比我外推的快。
- P2 命中：code 1.50 / 1.51 / 1.43 / 1.28×（押 1.6 / 1.5 / 1.4 / 1.25）。
- **P3 落空，错在"会变慢"那一侧**：prose 1.12 / 1.27 / 1.24 / 1.23×，128k 仍快 23%；押的是 64k 起不快、128k 0.9×。
  我按"宽 5 的校验"外推，但散文每轮只起草 2 个（校验宽 3），而且一轮的耗时随上下文跟单步 decode 几乎同比例涨（一轮 ÷ 一步 1.8 左右不动）。
- P4 命中：同一任务各档接受率 code 71–83%、prose 56–63%，没有随上下文单调变化（8k prose 56% 与 128k code 71% 是这两段文本本身，
  前缀不同 ⇒ 生成的内容不同）。
- P5 一半：变慢（code 的加速从 1.5 掉到 1.28）主要来自一轮相对单步变贵（2.50 → 2.76 倍），接受率没掉；但涨得很温和，不是悬崖。
  散文的比值不涨，所以散文的加速不缩。
- P6 落空：8 个贪心格子里开/关文本**全都不同**（每边 3 次内部一致）。kv8 下已知（SPD-018），这里连 code 也分叉。所以每格开/关比的是
  同一题的两段不同文本；3 次重复的离散很小（最大 8%），结论不靠单段文本。
- 采样行：code 1.40×（贪心 1.51），**prose 1.02×**——在贪心 1.27× 的同一上下文上几乎打平。采样下一轮比贪心同宽度贵约 10 ms
  （prose 74 对 64 ms，起草数相同），加上接受率 54% 对 63%。owner 的真实 agent 流量正是采样的散文 + 工具调用。
