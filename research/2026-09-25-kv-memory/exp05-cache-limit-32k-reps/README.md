# exp05：32k 的 decode 到底慢不慢——缓冲池上限 不设 / 1 GiB / 4 GiB，kv8 与 kv16，条件交替两轮，每条件 5 次

日期 2026-09-26（00:20 前后起跑）。m3u（M3 Ultra，96 GB），lmk worktree `kv-memory`，引擎 42a248c，mlx 0.32.0。常驻服务停着（2026-09-25 22:49:03 起）。

## 为什么加这一组
exp02（kv16）与 exp04（kv8）的 128k 行都清楚：1 GiB 上限慢 ≤ 1%。但 32k 行离散太大，分不出有没有效果：
- exp02 kv16 32k：不设限 51.0–51.3（两轮 6 次），1 GiB 47.2 / 50.6 / 51.9，4 GiB 51.1–51.2；
- exp04 kv8 32k：不设限 38.7 / 41.3 / 43.5 与 43.6 / 43.7 / 41.2，1 GiB 37.1 / 36.9 / 41.6（输出逐字相同、草稿轮数相同）。
1 GiB 的 5 个数里 3 个落在不设限的最低值以下。要么 1 GiB 在 32k 上真有几个百分点的代价，要么是离散。

## 条件与方法
与 exp04 同一 harness（拷来）；只量 32k、code、贪心；每条件一个临时 lmk、warm 1 次 + 5 次 256 token 解码（请求后读数窗口 3 s）。
条件顺序（每种精度一个 cache 目录，第一个条件冷算前缀）：kv8 不设 → 1 GiB → 4 GiB → 不设 → 1 GiB → 4 GiB，然后 kv16 同样六个。交替是为了把漂移（温度、时钟）分摊到各条件。

## 预期（跑之前写）
- **R1**：kv16 32k 1 GiB 与不设限的中位差 ≤ 2%，4 GiB ≤ 1%。把握：中（exp02 1 GiB 三次里只有第一次偏低）。
- **R2**：kv8 32k 1 GiB 慢 3–8%，4 GiB ≤ 2%。把握：低——kv8 的量化注意力每步的临时量比 kv16 多（反量化的中间结果），1 GiB 可能挡住复用；
  但同一路径在 128k 上 1 GiB 只慢 1%（exp04），与"临时量随上下文涨"的解释相矛盾，所以也可能只是离散（那就 ≤ 2%）。
- 同一精度下十个条件的输出逐字相同。把握：高。
