# exp02：自检看不看得见"丢了上下文"

起因：owner 的 itest（`../raw/itest2.log`）里把恢复后的线性注意力递归状态清零，surprise 反而**更低**（intact 2.05 对 corrupt 1.29）。
那次的新一轮里把代号表又完整列了一遍"供参考"——段内自己能预测自己，测不出上下文。

## 设计
- 历史（约 700 token）：26 个代号各配一个周次，只出现在历史里。
- 新一轮（被打分的段）：用户消息给出一个"工具结果"，按原顺序逐行写 `codename: week N`，**不在段内重复第二遍**。
  完好的上下文能从历史里抄出每一行；丢了上下文，代号和数字都不可预测。
- 损坏方式（都在恢复之后、prefill 之前，经 `RESTORED_CACHE_HOOK`）：
  - C1 递归状态清零（`ArraysCache` 全 0）
  - C2 全注意力 KV 沿序列打乱（keys / values 同一置换）+ C1
  - C3 全部清零（递归状态与 KV 都为 0）
  - C4 换上另一段对话的状态：先 prefill 一段同长度、内容无关的历史，存下它恢复出来的 cache 对象，再塞给这次请求（最接近"恢复了错的东西"）
- 每种各跑一次，记 surprise mean / p90，打分 token 数。

## 预期（跑前写）
- intact：均值 < 1.5 nats（大半是逐行抄历史）。把握：中。
- C1：可能仍低（全注意力层还能抄，上次就是这样）。把握：中。
- C2、C3、C4：均值比 intact 高 ≥ 1.5 nats。把握：中高——代号是自造词，没有历史就只能靠猜。
- 如果 C4（错的上下文）与 intact 分得开，就足以证明检查能看见 000193 那类"模型不认识自己的对话"。
