# exp07：Gemma 4 31B（稠密）——同尺寸档的第二个家族选择

日期 2026-09-22。起因：我说"和 27B 同档，价值不大"，owner 反问"what makes you think those LLM models are like commodity?"——用测量回答。
`lmk pull` HF 当前版本 `lmstudio-community/gemma-4-31B-it-MLX-4bit`（盘上 oMLX 那份不用）。常驻测试期间停。

## 预期（跑之前写）
1. 集成测试关/开 **5/5 ×2**。把握：中高（同家族，方言现成）。
2. 装载后约 17 GiB ⇒ "至少 32 GB"组，与 27B-4bit 同组。把握：高。
3. decode：稠密 31B-4bit 每 token 约 17 GB ⇒ 比 27B-4bit（16 GB，39.5）略慢，**34–38 tok/s**；prefill **约 300**。把握：中。
4. agent 任务：三轮缺省采样。12B 的循环/漏参数在 31B 上**不复现**（更大的稠密模型更稳）。把握：中低——这是本实验真正要回答的。
5. 不预设"和 27B 同档"。差异记在页面 Known issues / good for。

## 结果（2026-09-22，raw/）
| | 预期 | 实得 |
|---|---|---|
| 集成测试 关/开 | 5/5 ×2 | **5/5 / 5/5** ✓ |
| 装载后 / 分组 | 17 GiB，32 GB 组 | 17.15 GiB，**32 GB 组**（该机型约 39k 上下文；KV 80 KB/token 是列表里最大的） ✓ |
| decode | 34–38 | **33.0** ✗（略低于预期下限） |
| prefill | ≈300 | **252** ✗ |
| cached prefill | — | 26k（27B 是 53k：KV 更大，取回更慢） |
| agent 任务 ×3 缺省采样 | 全对 | **9/9 全对** ✓，工具步 60–100 token |

对照 27B-4bit：三个速度都慢（252/26k/33 对 323/53k/39.5），同内存下上下文更短；行为上是 Gemma：缺省不思考、直接答。
"和 27B 同档价值不大"这句被证伪的部分：它给 32 GB 档提供了另一个家族、另一种行为，且在 agent 小任务上和 27B 一样稳；
没被证伪的部分：速度和 cache 效率上它确实不如 27B。质量高低要难任务才能分出，本实验没量。⇒ 进表，页面把差异写清让客户自己选。
