# exp06：Gemma 4 12B 与 E4B——给小内存 Mac 的两个

日期 2026-09-22。m3u。`lmk pull` 拿 HF 当前版本（12B f45bda56，6.7 GB，稠密，`gemma4_unified`，262k；E4B ce713a00，6.8 GB，`gemma4`，131k）。
家族方言已有（exp05），本实验不改推理代码。常驻测试期间停。

## 预期（跑之前写）
1. 集成测试，关/开：**两模型都 5/5 ×2**。把握：中高——同家族同模板；`gemma4_unified` 是新 model_type，引擎的窗口拟合认
   `gemma4` 前缀应能覆盖，但没验证过。
2. 装载后占用：12B 约 7.5 GiB，E4B 约 7 GiB ⇒ 分组落在 **"至少 16 GB"**（0.81×16=13 ≥ 7.5+3，余 2.5 GiB < 4 ⇒ 实际会落到 24 GB）。
   按现在的 4 GiB 门槛，两个都是 **24 GB** 组。把握：高。
3. 速度：稠密 12B-4bit 每 token 约 6.7 GB ⇒ decode 约 27B-4bit 的 2.4 倍，**80–100 tok/s**；E4B 更小，**120+**。把握：中。
   prefill 12B 约 600–800；E4B 1000+。把握：低。
4. 三个 agent 任务：12B 3/3；E4B 至少 2/3（小模型的工具参数类型可能出错）。把握：中低。

- **F5 切分器只在开头认思考标记**——12B 思考关时先想一段、关掉、再吐一个空 channel 才发工具调用，第二个 channel 被当正文。
  ⇒ 正文阶段也认 think_open（对 Qwen 同样更正确）。
- **F6 12B 不可靠**：工具结果后贪心解码进入重复 `<|channel>thought` 的循环，缺省采样下三轮仍中一次；"前 5 行"三轮漏 `max_lines` 两次。
  达不到"和真实 agent 跑通"的门槛 ⇒ **不进表**，README 写明试过与原因。权重留在 HF cache（6.7 GB）。
- **E4B 反而稳**：四轮全对，代价是啰嗦（工具步 70–160 token，26B-A4B 是 21–43）。进表，"至少 16 GB"组。
- decode 两个都猜高了：我按"字节少就快"推，稠密小模型每 token 读全部权重，MoE 只读激活的——26B-A4B 的 2 GB/token 比 12B 的 6.7 GB 少。
