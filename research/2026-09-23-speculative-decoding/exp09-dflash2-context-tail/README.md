# exp09：DFlash 2 只拿到 prompt 尾巴的隐状态时，接受率掉多少（B 的设计点：命中磁盘 cache 时草稿器没有前缀）

日期 2026-09-24。m3u。mlx-vlm 0.6.16（lmk 的 .venv，引擎已升级到它），主模型 27B-4bit，草稿器 `incoai/Qwen3.8-27B-DFlash2`（bf16）。
机制（读 0.6.16 `speculative/dflash.py` 与 `drafters/qwen3_dflash/dflash.py`）：prefill 用 `capture_layer_ids=[5,19,33,47,61]` 拿到整段 prompt 的
5 层隐状态，草稿器第一轮把它们投影成自己 5 层的 K/V（滑窗 2048），之后每轮只注入新接受的那段。**命中磁盘 cache 的请求目标模型不算前缀**，
草稿器就只有本次实际 prefill 的尾巴。这个实验模拟"尾巴有多长"。

## 怎么量（`run.py`）
prompt = bench 的 4,034 token 填充文本 + 代码题（LRU cache 类），贪心 400 token。臂：普通解码（sha 基准）；DFlash2 上下文 = 全部（约 4.1k）/ 最后 1024 / 256 / 32 个 token。
每臂重新 prefill；记 tok/s、轮数、每轮接受、sha 是否与普通解码一致。用 mlx-vlm 自己的 `_dflash_rounds`。

## 预期（跑之前写）
- E1 全上下文：与 exp07 同量级（code 1.2×、每轮 4.3），sha 一致。把握：高。
- E2 上下文越短接受越低，但代码题主要靠最近几十个 token：最后 256 时每轮接受 ≥ 3.5，最后 32 时 ≥ 2.5。把握：低——这正是要量的。
- E3 sha 始终一致（目标模型校验，与草稿器看到什么无关）。把握：高。
- 判据：最后 256 若 ≥ 全上下文的 80%，B 走"草稿器只用本次 prefill 的尾巴"（不改 cache 格式）；否则要把草稿器 K/V 存进磁盘 cache。

## 过程与结果（`raw/run.log`、`raw/*.json`）
prompt 4,041 token；普通解码 36.5 tok/s（sha dd5d5e9d77）。

| 草稿器拿到的上下文 | tok/s | 倍数 | 每轮接受 | 接受 / 草稿 |
|---|---|---|---|---|
| 全部（4.1k） | 42.1 | 1.15× | 4.40 | 309/362 |
| 最后 1024 | 42.9 | 1.18× | 4.40 | 308/362 |
| 最后 256 | 42.9 | 1.18× | 4.35 | 308/366 |
| 最后 32（只有请求本身） | 43.2 | 1.18× | 4.12 | 303/360 |

- **E2 超预期**：只给最后 256 个 token 接受率不掉，只给最后 32 个也还有全上下文的 94%。草稿器主要靠最近的 token（和它自己刚生成的），远处上下文几乎不贡献。
  ⇒ **判据满足：B 走"草稿器只用本次真正 prefill 的那段"，不改磁盘 cache 格式。** 命中时前缀不给草稿器，agent 每步新增的几百 token 正好在它 2048 的窗口里。
- E1 略低于 exp07 的 1.22–1.27×（这里 1.15–1.18×，prompt 长 10 倍，目标步稍慢），每轮接受 4.4 同量级。
- **E3 落空，但原因在 harness 不在草稿器**：四臂输出彼此一致（同一个 sha e2f7daa133），却与 `generate_step` 的普通解码不同；exp07 走 `generate_step` 的草稿路径时
  三题逐字节一致。差别是这次我自己分块 prefill（带 `capture_layer_ids`）并自己采首 token。接进引擎后按引擎的正路（同一个 prefill、同一个采样）验证逐字节。
