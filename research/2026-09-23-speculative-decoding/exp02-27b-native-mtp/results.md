## 对照预期
- none ≈ 39.5：**命中**（38.3–38.8；比 exp01 顺序路径低 2%，同一底座两层封装的差别）。
- 加速 story 1.5–1.8× / code 1.8–2.2× / copyedit ≥2.5×：**全部猜高了**。实得最好设置（b3）story 1.22× / code 1.59× / copyedit 1.70×。
- 猜错的地方不是接受率——接受率比想的高：story 每轮 2.14 个（b3）、code 2.80、copyedit 2.96（几乎全中，b6 达 5.78）。
  猜错的是**草稿一步的代价**：预期 ≈ 主模型单步的 1/11（按读的字节算），实得 **≈ 0.37–0.42 步/每个草稿 token**
  （步/轮 ≈ 1 + 0.4×b，三种题一致，说明是固定开销不是题目差异）。一层 bf16 + 248k 词表的 lm_head，读的字节少但 kernel 多、
  每个草稿 token 一次 Python 轮回；主模型验证一个 block 还要过 48 层 linear attention 的状态回滚。这是实现开销，不是原理上限。
- block size：story 上 b=2 最好、b≥4 白干，**命中**；copyedit 上 b6 最好但只比 b3 多 3%，b4/b6 "明显赢"**没命中**——草稿贵，多猜不划算。
- 逐字节相同：code、copyedit **相同**（sha 一致）；story **不同**——第 189 字符起 "settled in his bones" 变成 "settled into the marrow
  of his bones"，之后全文分叉。贪心下分叉只可能来自数值：验证时一次前向算一个 block 的 logits，和单 token 逐步算的数值不完全一样，
  近乎平手的词就翻了。散文这种平手多，代码少。**不是错误输出，但不是"同一个模型"——进产品前要定义可接受的差异并加测试。**

## 落到判据（设计文档 §3：≥1.8× 先投机解码，≤1.3× 先 KV 量化）
- B=1、mlx-vlm 原样：散文 1.2×，代码 1.6×，复述 1.7×——**灰区，没过 1.8×**。agent 负载（代码、工具调用、改文件）偏向 1.5–1.7 这头。
- 但判据设立时的前提变了：当时以为投机解码要"搬实现"（一两千行），现在知道 mlx-vlm 在引擎钉住的这一版就已经实现了
  批处理版的 MTP 轮回（`_mtp_rounds_batch`）和混合注意力回滚，**fork 的活是接线**（BatchedVisionModelKit 加载草稿器、
  批生成循环走 `run_speculative_rounds`、磁盘 cache 块与回滚对齐）。KV 量化同理：mlx-vlm 已有 `BatchQuantizedKVCache`/turboquant。
- 每个草稿 token 0.4 步的开销是最大的可优化项；若能压到 0.15 步，同样接受率下 b3 的代码题就是 2.3×。这是 fork 之后的事，不是决策前提。
