# lmk 的开箱体验（OOBE）

日期 2026-09-20。状态：SAD 进行中。起因：owner——"As an AI agent developer, I don't have too much interest to
play with multiple model on my local m3u… most of the framework are over complicated, and their user experience sucks."
前提：实测 lmk 是 m3u 上跑 qw38-27B 体验最好的方案（research/2026-09-20-local-server-survey，SVY-005/006）。

## 0. 用户是谁、要什么
AI agent 开发者，有一台 Apple Silicon 机器。产品是他的 agent；本地模型是水电。他要的是**一个地址**：
填进 agent 的配置，从此每一步亚秒出字、重启后还在。他不想逛模型、调参数、管进程。

## A. 定位与命令面 —— 已裁（2026-09-20，owner："I like this direction"）
**lmk 是 appliance：一台机器，一个模型，常驻常热。** 用户拿到的是一个地址 + 一个 model id。
明确不做（写进 README 当立场，不是"以后补"）：模型库浏览、多模型同驻、每模型参数面板、菜单栏应用、网页管理台。
换模型 = 改成另一个再 `up`，替换。
命令面随 B 的裁决从四个变五个：`pull / up / status / logs / down`。

owner 随裁决给的三条（分别并入 B、C）：
1. 配置在 `~/.lmk/config.yaml`，缺省就能跑，用户不配任何东西也能启动。
2. 下载模型要更显式。
3. 模型放哪个目录？HuggingFace 有个共享位置。

## B. 模型从哪来、放哪 —— 已裁（2026-09-20，owner："agree on most of them"）
事实（m3u 实查）：HF 共享目录是 `~/.cache/huggingface/hub/`（`HF_HOME` 可改），每模型 `models--<org>--<name>/{blobs,refs,snapshots/<commit>}`。
m3u 上同一批模型散在三处：`~/.lmstudio/models` 166G、`~/models`（oMLX）32G、HF cache 16G；Qwen3.8-27B-4bit 实体在 LM Studio
目录，HF cache 里只有 4K 空壳。

推荐：
- **lmk 不拥有模型目录。** 模型用 HF repo id 指名（`lmstudio-community/Qwen3.8-27B-MLX-4bit`），实体就在 HF cache。
  理由：生态里唯一的公共位置——`hf download`、mlx-lm、oMLX（`--hf-cache`）都认，不重复下 15G；断点续传、`hf cache` 清理都现成；
  snapshot 的 commit hash 直接当模型身份（替掉 persistcache 里"文件名+大小+mtime"那套自制指纹）。
  代价：`~/.cache` 可能被清理工具扫掉（重下 15G）；路径难看（用户永远不需要看见）。
- **下载是显式的独立动作 `lmk pull`**（owner 第 2 条）。15G、几十分钟、占盘、走网络——这种事不能作为别的命令的副作用发生。
  `lmk up` 发现模型不在：拒绝，并打印要敲的那一条命令。`lmk pull` 不带参数 = 拉配置里的那个模型。
- 逃生口：`model` 也接受本地路径（m3u 今天就是这种情况）。
- **模型清单**：实测过的模型列在 `config.yaml.example` 里（owner："a place user can find all our possible parameters and
  model list"），用户抄一行进 config.yaml。今天清单里只有 qwen3.8-27b 一家。
  我的读法（待他纠正）：清单 = "我们跑过、保证体验"的集合；`model` 同时接受任意 HF repo id / 本地路径，但 example 里写明那是未验证的。

## C. 配置 —— 已裁（2026-09-20）
- 位置 `~/.lmk/config.yaml`（owner 第 1 条）。**取代** 09-19 的裁决 `~/.kitten/lmk.yaml`：lmk 自立门户，状态全部收进 `~/.lmk/`
  （config、cache、app、logs）。m3u 上的迁移在实现时做。
- 零必填。端口缺省 1235；`context_length` 缺省 = 模型自己的上限（受内存约束时如实下调并说出来）——顺带了结"配 200k 实为 262k"；
  model id 缺省 = 一个稳定短名，不再是"目录名小写"。
- **两份文件，kitten 的做法**（owner 裁决；对照 `internal/config/seed.go`）：
  - `config.yaml`：不存在时种一份**全注释**的模板，此后程序永不碰，归用户。
  - `config.yaml.example`：归程序，每次启动按内容比对、不同就重写；全部参数 + 模型清单的大全，文件头写明"别改，抄进 config.yaml"。
  - 缺省值住在代码里（模板全注释 ⇒ 没有值冻在用户盘上）；新版本的新参数通过 example 到达用户。
- **被否：我的"文件可不存在 + 只放改过的项 + `lmk status` 显示来源"**。我担心的是"写出去的缺省值冻住"，kitten 的全注释模板
  已经解决了它，还多给了用户一个查全部参数的地方；而且与 kitten 同一套心智，用户只学一次。`lmk status` 显示生效值这一条保留。

## C2. 状态目录与 prefix cache —— 已裁（2026-09-20）
事实（m3u，2026-09-20）：现在在 `~/.kitten/lmk/cache/<模型身份>/`，每条记录一个 safetensors；跑了一天半 10G，约 5G/天；
lmk 无上限，只有引擎预算 162.81 GiB。同机 oMLX 的 cache 无人过问地涨到了 176G。

推荐：
- `~/.lmk/` 收下全部状态：`config.yaml`、`config.yaml.example`、`app/`、`cache/<模型身份>/`、`logs/`。卸载 = 删一个目录。
  `cache.dir` 可改（外接 SSD）。
- 被否：`~/Library/Caches/`（系统和清理工具有权随时清，而这个 cache 的价值就是活过重启）；HF 目录（别人的地盘）。
- `cache.max_size` **缺省 200G，可配**（owner 裁决；我提的 50GB 被否——那个数我自己也说不出依据，而命中就是这个产品的价值，盘比等待便宜）。整目录按最久未用淘汰——一条规则；换模型/升引擎留下的旧身份目录无人再碰，自然先被淘汰，不为它们写专门逻辑。
- `lmk status` 显示 cache 已用/**生效**上限。引擎自己还有一层预算（`disk_budget.py`：min(一个满窗口 cache 的体积, 空闲盘/4)，空闲 <10GiB 时为 0；
  本模型 262k 窗口下 = 162.81 GiB）。`cache.max_size` 是上界，生效值 = 两者取小；不为了凑满 200G 去改引擎的预算。
- 建目录时放 `CACHEDIR.TAG` 并 `tmutil addexclusion`（免 sudo），不进 Time Machine。

## D. 怎么装到机器上 —— 已裁（2026-09-20，owner："sure. let's try this way"）；前提已验证（OOBE-003）
事实：mlx-engine 无 pyproject/setup.py，不能 pip install；requirements 61 行含 3 个钉 commit 的 git 依赖（mlx-lm、mlx-vlm、outlines）；需 python 3.11。
推荐：`curl … | sh` 安装脚本，底下用 uv（静态二进制，自带下载 python 3.11 ⇒ 消掉隐藏前置）；全部落在 `~/.lmk/`；升级 = 再跑一遍；
`make install` 留给开发者。被否的路：Homebrew tap（第三方 tap 的 untrusted 拦截、61 个 resource、oMLX 在 m3u 上留下的双 launchd 任务）；
`uv tool install` / PyPI（引擎不是包）。
实验结果：uv 从零到环境可用约 20 秒（uv 2s、python 3.11 2s、61 行 requirements 16s），42 个单测全过。剩下的真前置是 **git**
（3 个 git 依赖；全新 macOS 首次调 git 会弹 Xcode CLT 安装框）——可试把 git 依赖改成 commit tarball URL 绕开，未测。

## E. 常驻与升级 —— 已裁（2026-09-20，owner："can not agree more"）
- `lmk up`：装 LaunchAgent（登录自启、崩溃自拉）→ **等模型加载完 → 自己发一句冒烟 → 才打印 ✓ 和地址**。60 秒没起来：把 stderr 日志末尾几行直接打出来。
  起之前先查端口被谁占、是否已有另一个 lmk；是就指名道姓地说并停手，绝不进入拉起-失败的循环（m3u 上 oMLX 双 launchd 任务循环五个月的教训）。
- `lmk down`：停服务并卸 LaunchAgent（重启后不再起来）；cache、配置、模型都留着。**没有"停了但还留着自启"的中间状态。**
- 升级 = 再跑一遍安装脚本，然后 `lmk up`。脚本只换 `~/.lmk/app`，不碰在跑的服务；`up` 发现在跑的比盘上的旧就重启换新（等旧实例退出再起新的）。
  引擎升级 ⇒ 模型身份变 ⇒ 旧 cache 作废：重启**之前**明说"这次升级换了引擎，cache 要重建，第一句约 40 秒"。
- 明确不做：自动更新。不联网查版本，不自己换自己。

## E′. 对 E 的修正：引擎升级不再作废 cache —— 已裁（2026-09-20，owner："agree"）
起因：owner 问"升级引擎之后为什么冷？什么引擎？为什么要升、常升吗？"
事实：引擎 = mlx-engine，钉在 `08f0c07`（2026-08-21）；升级理由只有新模型家族支持 / 速度内存改进 / bug 修复；上游节奏一阵一阵
（08-10→08-21 五个 commit，其后一个月零个）；appliance 用户模型跑得好就几乎没有理由升，我们自己一年几次。
"升级即作废"是 lmk 自己的规则（`persistcache.model_identity` 把引擎 commit 哈希进了身份），不是引擎的限制——为防一件很少发生的事
（新引擎读错旧记录），让用户每次升级赔上至多 160G cache 和全部会话变冷。
- **身份 = 权重（HF commit hash，兑现 B）+ `CACHE_FORMAT_VERSION`。** 引擎 commit 只写进 `layout.json` 备查，不进身份。
  本地路径的模型（无 HF hash）沿用现在的文件名+大小+mtime 指纹。
- 升级引擎这个"特意的动作"多一道集成测试：**旧引擎写下的 cache，新引擎接着用，命中数与输出一致**。过 ⇒ 版本号不动，用户的 cache 活过升级，
  无需告知；不过 ⇒ 版本号 +1，此时才用 E 里那句"cache 要重建，第一句约 40 秒"。
- 被否：我原来的"引擎 commit 进身份"（粗、省我的事、费用户的事）。

## F. 第一句的 37 秒 —— 已裁（2026-09-20，owner："y"）
服务端消不掉：agent 开口前 lmk 不知道它的 prompt；新 agent 的第一句必须算完整个前缀（约 3s / 1k token）。
会撞上的场合（经 E′ 修正后）：刚装好、换了 agent。（引擎升级仅在格式版本真的变了时。）
推荐——让等待看得见、只发生一次：
1. `lmk up` 成功后的输出里一句话说在前头："first request from a new agent prefills its whole prompt (~3s per 1k tokens); after that every step starts in about a second."
2. `lmk status` 显示在途请求的 prefill 进度（`server.py` 已在 `_in_flight[...]["prefill"]` 里记着，只差显示）。
3. 流里的 `lmk.prefill` chunk 保留：懂的 agent 画进度条；不懂的客户端忽略它，但连接上一直有字节，不会被 30–60s 读超时掐断。
   非流式请求在 prefill 期间一个字节都没有——README 写明"用流式"，不为非流式做保活。
- 不做：服务端猜 prompt、预热。预热只能由 agent 发起（`/lmk/v1/warmup` 已有），何时调归 G。

## G. agent 一侧 —— 已裁（2026-09-20）
- 别人的 agent（任何 OpenAI 兼容客户端）：`lmk up` / `lmk status` 把三样东西打印成可复制的形状——地址、model id、"api key 随便填"。
- kitten：**配置保持显式，不改**。`providers.lmk.base_url` 照旧必填（"写出服务器就是 opt-in"的旧裁决不动），别名照旧写全。
  lmk 这边能帮的是把要粘的那几行原样打印出来（含 kitten 的片段），并用稳定短名（C）让 id 不易填错；模型选择器本来就会从 status 列出常驻模型。
- **被否：`providers: {lmk: {}}` + base_url 缺省**（我的提议）。owner 原话："you are making things harder to understand. I prefer making
  thing more explicit." 少写两行的代价是读配置的人得去猜 kitten 连向哪里；行数少 ≠ 好懂。
- 不做：kitten 启动时探测 1235 端口自动发现（隐式、启动期 IO、违反"注册只看配置"）；开会话时自动 warmup（维持上一个 SAD 的"推迟"）。
- kitten 发"用途 + refId"头：属于 2026-09-19-llm-call-flow-control.md 里待裁的 C，不在此重复。

落地时定的细节（设计里没写到的）：
- 三种指名方式是三个键 `model.name / repo / path`，只能写一个——显式优先，不靠一个字符串猜它是名字、repo 还是路径。
- `lmk pull` 不带参数：拉配置里的那个。配置是唯一的事实来源；换模型 = 改配置 → `pull` → `up`。
- `lmk up` 靠"配置指纹"（build + 生效配置 + 模型 revision 的哈希，服务在 status 里报出）判断要不要重启；相同即 no-op（0.16s）。
- `lmk serve` 遇到重启也修不好的问题（配置错、模型缺、端口被占）**干净退出**（exit 0），launchd 的 `KeepAlive.SuccessfulExit=false`
  因此不会空转——m3u 上 oMLX 那个每 11 秒一次、转了五个月的循环就是反例。
- 非缺省 `LMK_HOME` 的安装不往 `~/.local/bin` 放 `lmk` 链接（测试时踩到：临时安装劫持了命令）。
- launchd label 沿用 `ai.kitten.lmk`：换 label 会让新旧两个服务抢端口，正是要避免的那类事故。
- 给人看的字集中在 `render.py`、`configfiles.py` 的模板、`install.sh` 的输出、README——都按"没参加过我们讨论的 agent 开发者"来写。

实测时踩出来、已修的两个坑：
- `lmk` 命令用 `python -m lmk` 起，cwd 排在 import 路径最前：在本 repo 的 clone 目录里敲 `lmk`（README 正是这么教的）跑的是工作树的代码。
  → 命令与 launchd 都用 `python -P`。是 `make install` 第一次走升级路径时暴露的。
- mlx-engine 一被 import 就把 `huggingface_hub.snapshot_download` 换成必抛异常的函数；用它找本地模型，成败取决于进程先 import 了谁。
  → `models._hf_snapshot_dir` 直接读 HF cache 的目录结构。是集成测试（先 import 引擎、后找模型）暴露的。

未验证：重启机器后 launchd 自动拉起（自第一版起未验证）；`curl | sh`（repo 私有）；16GB 以外内存规格的机器。
下一步（OOBE 之外，已排队）：内存护栏、采样参数（engine 层的 `sampling` 直通已就位，缺 HTTP 层解析）。
