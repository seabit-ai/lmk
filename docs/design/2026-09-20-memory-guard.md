# lmk 的内存护栏

日期 2026-09-20。状态：SAD 进行中。事实依据：`research/2026-09-20-memory-guard/notes.md`（MG-001..005）。

## 0. 用户要的结果
**这台 Mac 不会因为 lmk 而卡死。** 卡死 = 所有 agent 一起停、只能硬重启，是本地跑模型最贵的一种失败。
次一级：当 lmk 因为内存拒绝做某件事时，它说得清为什么、该怎么办。

## 1. 已有的与缺的
引擎已经做了最难的那部分（MG-001：按实测系数把窗口拟合进 GPU 工作集，并按内存排 prefill 步长）。缺的是它假设之外的三种情形：
| | 情形 | 谁造成的 | 现状 |
|---|---|---|---|
| ① | 配了一个这台机器装不下的模型 | 用户的配置（只可能经 `model.repo` / `model.path`） | 无检查，照常加载（MG-003） |
| ② | 几个长请求同时在跑 | lmk 自己（`max_seq_nums=4`） | 拟合不知道并发（MG-002） |
| ③ | 别的程序在同一台机器上加载了大模型 | 邻居（oMLX / LM Studio / …） | 拟合看不见别的进程，且只算一次（MG-004） |

## 2. 设计点
（逐点过；裁决与被否方案记在各节）

### A. 护栏管哪几种情形 —— 已裁（2026-09-20）
三种都管，各用最便宜的手段。原则：**lmk 对自己造成的风险负全责；对邻居造成的风险，只保证自己不再往里加内存。**
- ① 加载前检查（已同意）：`lmk up` 拿权重体积比 GPU 工作集，装不下就拒绝并说清"要多少、这台 Mac 给多少"。
- ② 并发：见 B。
- ③ 邻居（已同意）：读 macOS 的内存压力等级；到"危急"时拒绝**新**请求并明说，`lmk status` 一直显示压力等级。不卸载自己、不杀别人。
- 明确不做：每秒轮询内存的守护线程；内存不够时自动卸载模型；悄悄调小用户配置的窗口（引擎已在做，且 status 如实显示）。

### B. 并发 —— 已裁（2026-09-20）
事实（MG-006，exp01）：并行**生成**给吞吐——2 个同时 1.7×（各 34 tok/s，单个 39.7），4 个同时 2.2×（各 22）；
读 prompt 严格串行；**一个请求读长 prompt 时，所有正在生成的请求近乎停顿**（读 13k 用 43 秒，期间另一个只出 11 个 chunk）。
并发 4 个无错无卡。

**B1（已裁）：同时作答的请求数可配置，缺省 2。** 原话："should be something we can configure, maybe we set default to 2."
- 配置项 `requests.max_parallel`（缺省 2）；传给引擎的 `max_seq_nums`。超出的请求被接受并排队，不报错。
- 缺省取 2 的依据是实测：2 拿到了大部分收益且每个请求几乎不变慢；4 让每个请求掉到约一半。模板注释里写明这组数字出自
  M3 Ultra + 缺省模型，别的机器/模型需自己量。
- 内存：两条满长序列 ≈ 32GiB KV + 15 + 3 ≈ 50GiB，在 77.76GiB 之内；缺省值下并发的内存风险顺带了结。
  用户把它调大时，上限检查归 A① 的同一处（`lmk up` 时按 `max_parallel × 窗口 × 每 token KV` 核一遍，超了就拒绝并说清）。
- 被否：我最初的"写死降到 2"。

**B1 的依据需补上条件（MG-008，exp03，落地后才量到）**：exp01 的 1.7× / 2.2× 是在几十 token 的短 prompt 下量的，数字没错，缺的是条件。
27k 上下文下 1 个 33 tok/s、2 个各 16，合计 1.0×。两组数并列才是完整的事实：并行的收益随上下文长度而变（中间的长度没量过）。
产品里的说明文字改为两种条件并列陈述。**缺省值保持 2（owner 重裁，2026-09-20）**：长上下文下它不换来吞吐，换来的是
后来者立刻半速出字、而不是整段停着等——盯着一个会话看的人，半速仍可读，停住更难受。
（owner 纠偏："it's not an error, it just needs to be more precise on condition"——我先是只报 1.7× 不写条件，量到 1.0× 后又说成"推翻"，两头都不精确。）

**B2（已裁，"agree"）：有请求正在作答时，新来的长 prompt 先排队。**
正在作答的请求写完之前，不开始读新请求的 prompt（短到一块以内的除外——它一圈就读完，不拖人）。
理由：一次作答通常几秒到几十秒，让后来者等这一会儿，远小于让正在看输出的人停 43 秒。`lmk status` 显示
"waiting — another request is answering"及是谁。lmk 自己的准入逻辑，不改引擎。
- 可行性（已查）："长"要按**未命中 cache 的 token 数**判——agent 的每一步都是 27k prompt、只有几十个新 token，绝不能被排队。
  引擎的 store 有 `plan_longest_prefix_restore(...)`：只查内存里的索引、不加载记录，准入前即可问"这条 prompt 会恢复多少"。
  待实现时核实：该方法从 HTTP 线程调用是否安全（store 归 cache I/O 线程所有）；带图片的请求哈希含图片，算不准时按"长"处理。

### C. 两个请求并行时的内存账 —— 已裁（2026-09-20，"I like C"）
引擎的窗口拟合按"一条序列"算；缺省并行 2 在小内存 Mac 上会超（32GB：工作集约 22GB − 权重 15 − 余量 3 ≈ 4GB ≈ 65k token 的 KV，
两个 50k 的请求就超）。
- **按 token 记账**：加载后用引擎实测的每 token KV 字节数算出"这台机器总共装得下多少 token 的 KV"；新请求进来时，
  在途的（prompt + max_tokens）之和加上它若超过总量，就在 B2 的同一个准入队列里等。单个请求仍可用满整个窗口。
- m3u 上总量约 98 万 token，永不触发；保护的是小内存机器上的用户。status 对等待者显示原因。
- 被否：静态平分（窗口 ÷ 并行数）——最常见的"只有一个请求"时，单独装得下的长对话会被拒。
- 局限：只有一台 96GB 的机器，小内存上的行为无法实测；逻辑由单测保证（假引擎注入小总量）。

### D. 加载前检查怎么判 —— 已裁（2026-09-20，"agree"）
- 判据只有一条：**权重体积（目录里 *.safetensors 之和）+ 3GiB 余量 > GPU 工作集上限 ⇒ 拒绝启动**。
  3GiB 沿用引擎拟合用的同一个余量（`context_fit.py`：来自实测残差）。工作集上限 = `mx.device_info()["max_recommended_working_set_size"]`，
  不加载引擎即可读（m3u：77.76GiB，0.03s）。
- 只比权重：权重装不下 = 必然失败；"装得下但窗口要缩"已由引擎的拟合处理，`lmk status` 如实显示。
- 两处：`lmk up`（起 launchd 之前，立刻得到答复）；`lmk serve`（防绕过，干净退出，launchd 不空转）。
- 拒绝时说清三件事：要多少、这台 Mac 给多少（以及为什么不是全部内存）、该怎么办（更小的模型 / 更低 bit）。
- **不提供强行加载的开关。** 有开关就会被关掉（09-19：为加载大模型，LM Studio 的护栏被 agent 关了）；权重大过工作集的模型没有任何场景值得强行加载。

### E. 邻居把内存吃紧时 —— 已裁（2026-09-20）
- 信号：macOS 自己的内存压力等级 `kern.memorystatus_vm_pressure_level`（1 正常 / 2 警告 / 4 危急）。系统对"整机还撑不撑得住"的
  综合判断，已算进所有进程；读一次几微秒。
- **只报数字，不猜原因**（裁决："we just report the memory numbers"）。`lmk status` 常驻一行：
  `memory  pressure: warning · 12% of 96 GB free · lmk holds 19.2 GB`——压力等级、`kern.memorystatus_level`（全机空闲百分比）、
  MLX 报告的本进程 GPU 内存。三个都便宜、可靠。
  被否：我的措辞 "another program is using a lot"——lmk 不知道内存被谁吃了，也可能就是它自己；没核实的原因不进给用户看的字。
- "警告"：不改变任何行为，只显示。"危急"：新请求**不放行**（见 F 的队列）；已在作答的继续写完。
- 不做：危急时卸载模型；数别的进程、杀进程；对"警告"做任何动作。

### F. 一个等待队列，四条准入规则 —— 已裁（2026-09-20，"y"）
起因：owner 三问——内存造成的等待与并行数造成的等待要不要分开处理？有没有可配置的最长等待？有没有可配置的队列上限？
- **不分开。** lmk 里、引擎前面，**一个**先到先走的队列。队首依次过四条规则，全过才交给引擎；过不了就留在队首，后面的跟着等：
  ① 在答的请求数 < `max_parallel`（B1）；② 有请求在答时，未命中 cache 的部分超过一块的新请求先等（B2）；
  ③ 在途的 token 账装得下它（C）；④ 内存压力不是"危急"（E）。
  `lmk status` 对每个等待者显示卡在哪一条及当时的数字。
- 重新检查：有请求结束时查一次（①②③ 只在这时变）；④ 由外界决定，**仅当队列非空时**每秒查一次。
- 并行数由 lmk 自己数，不再靠引擎内部的队列（那个队列在引擎里，看不见）；`max_seq_nums=max_parallel` 仍传给引擎作兜底。
- **放行之前不发任何字节（含状态行）**：等过头可以老实回 503。已查 kitten 的 lmk 客户端无读超时（ctx 管）。
  被否：等待期间发 SSE 注释行保活——会让超时变成"先 200、后流内报错"。
- 配置（都在 `requests:` 下，名字带单位）：
  | 键 | 缺省 | 缺省值的依据 |
  |---|---|---|
  | `max_parallel` | 2 | exp01：2 个同时 1.7×、各自几乎不慢；4 个各掉到约一半 |
  | `max_queue` | 16 | 多会话形态：6 个会话 × 一个 turn + 一个 groom = 12，留余量。满了的下一个立刻 503 |
  | `max_wait_seconds` | 600 | 一次合理的最长等待：前一个读完 10 万 token 的冷 prompt（约 5 分钟）+ 写 8k token（约 4 分钟） |
- 命名：`max_queue`（owner 改定；我原先写的是 `max_waiting`——队列就叫队列）。
- 一个最长等待管所有原因。被否：我上一轮的"内存危急单独等 60 秒"——等待者什么都不占，等 10 分钟无害，且用户看到原因后可以去关掉
  吃内存的程序让它继续；60 这个数本来也没有实测依据。
- 503 的报文写清：等了多久、卡在哪条、当时的数字；队列满则 `16 requests are already waiting`。
- 每次进入/离开"危急"记日志（带持续时长）：将来回头校数值的依据。
