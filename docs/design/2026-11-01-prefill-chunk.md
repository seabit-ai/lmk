# prefill 块缺省 512：另一个请求不再冻住 7 秒

> 2026-11-01 owner "agree. go on." → "yes, do them now" → "ok, do it"（先量再改）。实现：fork `lmk` 分支一行
> （`PROMPT_PROCESSING_CHUNK_SIZE` 2048 → 512，commit `e863778`），lmk 分支 `prefill-chunk`。取证：
> `research/2026-11-01-sink-mask-review/notes.md`（SMR-009..013，exp02–05）。

## 起因
Robert Price（blackweb.ai）10 月 17 日来信（推销信，看了我们公开的 exp05 smoke 脚本）说量化 KV 下 2048 的
prefill 块让 Metal 峰值内存比 fp16 高 66–73%，改 512 省一半。另一个 agent 据此在 fork 里加了"量化时才降到 512"。
复核时发现他的数来自 mlx-lm 的 convert 路径（fp16 与量化 cache 并存），lmk 的批处理路径从第一个 token 起就建量化
cache，数字搬不过来；于是在 lmk 自己的路径上量。

## 事实（M3 Ultra 96 GB，单次运行，exp 编号在 research 里）
| | 27B-4bit @2048 | 27B-4bit @512 | E4B-4bit @2048 | E4B-4bit @512 |
|---|---|---|---|---|
| 50k prompt 峰值（fp16 cache） | 25.5 GB | 20.8 GB | 10.7 GB | 9.5 GB |
| 50k prompt 峰值（kv8） | 24.2 GB | 19.5 GB | — | — |
| 50k prefill 秒 | 187 | 189 | 20.1 | 22.0 |
| 另一个请求在 30k prefill 期间每个 token 的间隔 | 6.7 s | 1.8 s | 未量 | 未量 |
| decode | 不变 | 不变 | 不变 | 不变 |

- kv8 的峰值比 fp16 **低** 1.3 GB，不是高 66–73%（SMR-010）。
- 块变小省的那块内存与 cache 位宽无关（fp16 也省 4.7 GB，SMR-011）。
- 批处理生成器每读一块就给其它请求出 1 个 token，所以块的耗时就是别人等一个字的时间（SMR-012）。
- 引擎自带按请求的降块计划，但只在内存紧时起作用；96 GB 上永远是 2048（SMR-009）。

## 裁决
1. **缺省块 512，所有加载、所有模型。** 给用户的效果：一个 agent 读长 prompt 时，另一个 agent 的字 1.8 秒一个地出，
   而不是冻 7 秒；96 GB 机器上多出 4.7 GB 余量；内存紧的机器上下文能定得更长。代价：E4B 这类小模型 30k 以上的
   prompt 慢 9–11%（50k 多 1.9 秒，每段对话一次）。
2. **准入队列的 `SHORT_PROMPT_TOKENS` 保持 2048。** 它原来的出处是"引擎一步"；现在改为"放行的 prefill 工作量上限
   （27B 约 7 秒）"。效果上 decoder 从一个 7 秒的冻结变成四个 1.8 秒的间隔，没有变差；降到 512 会让 1k–2k 的 prompt 开始排队，
   换不来任何可感知的好处。
3. **模型页的速度表不重测**：27B 的 prefill 在 512 下差 <1%（exp02/03），表仍有效；E4B 页加一行说明差 9–11%，重跑记在 backlog。

## 被否的方案
1. **量化时才降到 512**（fork 分支 `kv-quant-chunk`，Robert 原意）：省的内存和位宽无关，fp16 缺省的 96 GB 机器反而拿不到；已删。
2. **一刀切 1024**：27B 的卡顿只减半（约 3.4 秒一个字）、内存省 3.3 GB，为的是 E4B 少付约 1 秒。不值。
3. **按模型大小分档**（大模型 512、小模型 2048）：多一条用户要理解的规则，换 E4B 一段对话省 1.9 秒；引擎也没有"模型大小"这个现成的量。
4. **阈值跟着降到 512**：见裁决 2。
5. **靠引擎自带的 fit 计划**：它只在内存不够时降块，解决的不是卡顿。

## 没量的
122B / 26B-a4b / 31B 在 512 下的 prefill 速度（按 27B 推测 <1%，没量）；超过 2 个并发；256 等更小的块；
E4B 在并发下的卡顿（它 2048 一块只要 0.8 秒，本来就不太卡）。每臂只跑了一次；四臂在该一致的地方一致到 0.1 GB。
